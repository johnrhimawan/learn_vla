# Obstacle Reach RL Project

This project tests a case where demonstrations alone are a weak training
signal: the robot must select a language-specified target, avoid an obstacle,
and recover from an impulse. The simulator can score progress, collision,
speed, smoothness, and recovery on every transition. Collecting expert labels
for every possible failure would be expensive, while reinforcement learning
can optimize those outcomes directly.

## Task and information boundary

`obstacle-reach-v0` contains a 3-DoF arm, a red target, a green target, and a
blue obstacle. The two instructions are:

- `Reach the red target quickly without touching the blue obstacle.`
- `Reach the green target smoothly without touching the blue obstacle.`

The deployed policy receives `camera1`, six joint position/velocity values,
and the instruction. Target coordinates, obstacle coordinates, contacts, and
the disturbance trigger are private simulator state. They are available to
the reward and metrics, never added to the policy observation.

The held-out suite is fixed in
[`configs/eval/obstacle_reach_v0.json`](../../configs/eval/obstacle_reach_v0.json).
It contains both instructions, nominal episodes, and episodes with an impulse
at control step 20. Every controller goes through the same joint and slew-rate
limits in `ObstacleReachEnv.project_action`.

## Dataset

Generate the local LeRobot Dataset v3 warm-start set with:

```bash
scripts/collect_rl_seed_data
scripts/run python examples/inspect_dataset.py \
  artifacts/obstacle-reach-seed-v0 \
  --repo-id local/obstacle-reach-rl-v0
```

The default set has 20 balanced episodes from seeds 1100 through 1119. Every
episode gets a disturbance at step 10 and is generated by a damped
least-squares controller with local obstacle repulsion. The current generated
set has 596 frames, 100% task success, and no collisions. Seeds 1100–1115 are
the training partition and 1116–1119 are validation. Evaluation seeds start at
2100 and are never demonstrations. The complete specification is in
[`configs/datasets/obstacle_reach_rl_v0.json`](../../configs/datasets/obstacle_reach_rl_v0.json).

The dataset directory is ignored by Git because image data grows quickly. Copy
it to object storage or a versioned cluster path before training. Keep its
`meta/` files with the data; the baseline report hashes them so normalization
and action-unit calibration can be reproduced.

## Mac Mini inference and baseline

The Mac runs MuJoCo on CPU, rendering through the local graphics stack, and
SmolVLA inference on MPS. Reproduce both reference controllers with:

```bash
scripts/evaluate_rl_baseline expert --device cpu

set -a
source ~/.env
set +a
scripts/evaluate_rl_baseline smolvla-base --device mps
```

The SmolVLA evaluator verifies the pinned model SHA-256 before loading it. It
adapts the checkpoint's padded action projection to this environment's three
joint commands and uses dataset statistics to convert state/action units. It
does not run a task-specific optimizer step. This is therefore an untrained
task baseline with embodiment normalization, rather than a claim that the
SO-100 checkpoint is directly portable to an arbitrary arm.

The recorded base run succeeded on 2 of 4 held-out episodes (50%), while the
classical task expert succeeded on all 4. The base reached the green target in
both nominal and disturbed trials but failed both red-target trials. That
language-conditioned gap is the comparison point for imitation learning and
RL. Reports live in [`results/baselines`](../../results/baselines).

## H200 learner setup

Build the CUDA environment on an x86 Linux machine with an NVIDIA Container
Toolkit installation:

```bash
docker build -f docker/h200/Dockerfile -t learn-vla:h200 .
mkdir -p outputs
docker run --rm --gpus all --shm-size=16g \
  -v "$PWD/artifacts:/workspace/learn_vla/artifacts" \
  -v "$PWD/outputs:/workspace/learn_vla/outputs" \
  -v "$HOME/.cache/huggingface:/workspace/.cache/huggingface" \
  -e HF_TOKEN \
  learn-vla:h200
```

The image starts from NVIDIA's CUDA 13.0.2 runtime and installs the exact Linux
environment from `uv.lock`. That selects PyTorch 2.11 and its CUDA 13 wheels,
which satisfy LeRobot 0.6.1's `torch>=2.7,<2.12` requirement. The verification
command checks CUDA visibility, Hopper compute capability, bfloat16 matrix
multiplication, LeRobot, and MuJoCo. Set `MUJOCO_GL=egl` for headless rendering.
The container selects `scripts/run_h200`, which executes directly in the locked
CUDA virtual environment.

The intended topology is one H200 learner plus 16 CPU MuJoCo actors sharing an
off-policy replay service. Start with the parameters in
[`configs/rl/h200_residual_sac.yaml`](../../configs/rl/h200_residual_sac.yaml):

1. Freeze SmolVLA. At each replan it produces the base three-joint action and a
   frozen visual/language representation.
2. Train a small SAC actor that observes that representation, proprioception,
   the instruction embedding, and the base action. It emits a bounded residual
   `delta_action`.
3. Execute `clip(base_action + 0.10 * delta_action)` through the environment's
   safety projection. Seed replay from demonstrations and keep 25% demo
   samples in each batch during early training.
4. Evaluate every 25,000 environment steps on the immutable held-out suite.
   Save replay metadata, configuration, checkpoint hashes, and evaluation JSON
   with each checkpoint.

The first gate is at least 90% success over an expanded 100-seed suite with a
collision-episode rate below 10%. After residual SAC is stable, use replay
advantages to weight SmolVLA flow-matching updates, then distill the residual
controller into one deployable policy. Retain the residual version as the
diagnostic reference.

LeRobot's documented HIL-SERL implementation provides an actor/learner SAC
pattern, replay, and demonstration mixing, but it is a separate policy path
from SmolVLA. The frozen-VLA residual adapter described here is custom work;
the YAML is an implementation contract, not an executable LeRobot training
command yet.

Before residual RL, produce the behavior-cloning warm start on the H200:

```bash
docker run --rm --gpus all --shm-size=16g \
  -v "$PWD/artifacts:/workspace/learn_vla/artifacts" \
  -v "$PWD/outputs:/workspace/learn_vla/outputs" \
  -v "$HOME/.cache/huggingface:/workspace/.cache/huggingface" \
  -e HF_TOKEN -e SMOLVLA_BATCH_SIZE=64 \
  -e SMOLVLA_OUTPUT=outputs/smolvla-obstacle-bc \
  learn-vla:h200 \
  scripts/train_obstacle_bc artifacts/obstacle-reach-seed-v0 20000 cuda
```

This command is executable now. Preserve its output as the BC comparison and
as the base policy for the residual learner.

## Comparison protocol

Do not change evaluation seeds, action projection, reward, model revision, or
dataset metadata between the baseline and a trained checkpoint. Compare:

- success rate by instruction and disturbance condition;
- collision-episode rate;
- return and final distance;
- recovery success after the impulse;
- action variation and inference latency.

Run at least five policy-sampling seeds once training introduces meaningful
stochasticity. The four-case suite is a fast regression check; use the
100-seed expansion for a training claim.
